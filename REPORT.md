## 4. What the held-out mutants show

The reasons below come from the mutant diffs, the suites' test code and the runs in `bench/results-v2/holdout/`.

**h01, h02, h03: no suite killed them. This is a spec coverage gap, not a framework limit.** Each needs a request that none of the five suites sends. All 30 mutant runs exited 0.

| Mutant | Change | Request that reveals it | Why no suite sends it |
|---|---|---|---|
| h01 | `patient-role-policy` loses `operation.id: FhirRead` | Patient `GET Patient/<own id>/_history` | No spec case covers history. `_history` appears in the suites only when parsing transaction `location` URLs. |
| h02 | Observation `subject` check becomes a suffix `LIKE` | `subject=<other>,<self>` as a comma list | Spec case 6 does not name it. All five suites send a repeated `subject=` instead. No suite sends a comma list for `subject`. |
| h03 | Include guard loses case-insensitivity (`!~*` → `!~`) | `%5Frevinclude` with uppercase `F` | No suite sends a percent-encoded include. All use literal `_include` and `_revinclude`. |

Any of the five could send these requests. Whether each HTTP client preserves a raw `%5F` was not tested, because no suite tried. The held-out author worked from the policies and their README, so these mutants target behaviour the 15 cases do not name. Under this spec, 12 of 12 may not be reachable.

**h09 and h11: Hurl missed them, the other four killed them by decision assertion.** The mutants crash a policy on a request that is denied anyway, so only a crash check sees them. The suite has the requests but not the check, and this is a test-writing choice, not a Hurl limit.

- **h09** (repeated `subject=`, a crash on the denied path). `cases/06-search-leak.hurl` sends that request and asserts only `HTTP 403`, with no `__debug=policy` request beside it.
- **h11** (forged `$extract` answer, a crash on the denied path). `cases/09-sdc.hurl` does send the debug request, and asserts that no policy granted. It has no `error` check. A crashed policy still grants nothing, so the assertion passes.
- Neither file contains a crash assertion. In the other four suites, each deny goes through one line (`expect_deny`, `denies`, `helpers:decision` or `match r.verdict`) that includes the crash check. This Hurl suite has no shared assertion, so each crash check is written out per request.

Hurl does kill h10 and h12, through crash checks that it wrote in other files.

**h07: Karate and Playwright missed it.** The mutant lets the receptionist read `Encounter`. Spec case 8 says "5 identities × 4 operations" without naming them. Hurl, pytest and Tavern put an Encounter read in the matrix, and those three kill h07 there. Karate and Playwright chose four operations on Patient and Appointment, and no other test in either suite reads an Encounter as the receptionist. This is a coverage choice left open by the spec, not a framework limit.

**Decision-only kills.** On the held-out set, 2–5 kills per suite depend on a decision assertion, against 1 on the original 15. Without those assertions (the ablated copies), the suites keep only 5, 4, 4, 4 and 4 kills of 12 (Hurl, Karate, pytest, Playwright, Tavern).

Caveat: this set was built to contain such bugs. Ticket 17's brief asked for at least 3 and it holds 4 (h09–h12), each verified to leave status and body unchanged on the probed requests. So the 2–5 range measures how much the suites catch of a category that was deliberately included. It does not measure how common those bugs are.

Even so, the result supports checking the decision. Status alone cannot detect these bugs by construction. Hurl's two misses relative to the others are exactly the two requests where it skipped the decision or crash check.

One kill is not from that category. pytest and Tavern kill h06 only by decision, because their allowed-`$extract` checks deliberately stop at the policy gate, as spec case 9 permits. h06 does change the status, and Hurl, Karate and Playwright catch it that way.

## 5. Recommendation

**Use pytest + httpx as the single tool for new API-level and access-policy tests.** The first-draft reasons stand (Part B section 4), and best state adds to them:

- It ties for the highest held-out kill count (9 of 12) and has the highest score under every variation tested.
- It is still the shortest with helpers counted, despite gaining recovery and parallel code.
- Both of the first draft's build items are done: the transaction stamp is persisted, and the run opens outside xdist workers. Killed-run recovery is tested.

Use it sequentially at this size. Its parallel mode is safe but slower here.

**Keep the existing production suite running, and don't migrate it on this evidence.** Migration cost is still unmeasured. Best-state Hurl is also better than the first draft showed: fastest, and the only suite whose failure output got every diagnosis fully right, including the SQL for mutant 09. If it stays, add a crash check to every deny, since its two misses relative to the others came from leaving that out.

**Add these requests to whichever suite is used, or to the spec.** They close the three universal survivors and h07: `_history` on an own record, a comma-list `subject`, a percent-encoded `_include`, and every matrix identity against a clinical resource.

**What would change this recommendation.**

- **Against pytest:** nothing in the sensitivity check. A repeat of the authoring run with results well below 11 of 13, or the user's readability review changing several steps, would need to be combined with other changes. Its authorability score is first-draft and N = 1.
- **To Playwright or Karate for second place:** weight choice alone. Choosing between them should rest on team language or fixtures needs, not on this score.
- **To keeping Hurl for access policies:** the same cost argument as the first draft.
- **At larger scale:** a real measurement at the existing production suite's size.

## 6. Limits of the best-state numbers

- **Held-out set.** There is one set of 12 mutants, by one author, working only from the policies, their README, the fixtures and the tooling scripts. That author also opened `sut/fixtures/run.sh` by mistake (recorded in ticket 17). 9 of 12 is a small sample: the difference between 7, 8 and 9 kills is one or two mutants. Flakes are computed per set.
- **LOC after revision.** Best-state LOC includes parallelism, recovery and failure-output code added to meet the checklist, which the first-draft numbers did not have. Karate's reduction includes deleting case 15. The net change is not "effort": the git added/removed columns in `bench/results-v2/results.md` show the churn.
- **Time-to-diagnose.** Grades are the author's and await the user's spot-check. The 5 mutants are the same ones the revisers could run while improving failure output (revision item 4), so these results may flatter the suites. The agents are one model reading logs.
- **N = 1 revision per suite**, on one machine.
- **Style has converged.** Revisers could read each other's work and were pointed at `research/findings.md`. Hurl borrowed Playwright's crash probe, and pytest and Tavern share an approach. Best-state similarity across suites partly reflects that, so differences understate what independent teams would produce, and the frameworks are less independent than in the first draft.
- **DNS incident.** A failed Aidbox cold restart hung the bench for about two hours. No timed run was affected, since restarts are not timed, and the one unfinished cell was re-measured from scratch after it.
- **Hurl pin.** It runs 8.1.0 here and the existing production suite runs 8.0.1.
- **Runtime at production scale.** The runtime spread (1.6–5.4 s best mode) says nothing about the existing production suite. Hurl ran 134 requests here against far more there, per-request overhead was not isolated, and the suites differ in test count. The parallel gains (7% to 39%, and a loss for pytest) are at this size only.
- **Runtime scoring.** Band edges matter: Karate and Playwright are 0.15 s apart and land in different bands.
- **Authorability is frozen** at first-draft numbers with the confounders from Part B section 6: one run per framework, language familiarity, and differing extra reads. Tavern is still 0/13 despite 9/13 after one shared fix.
- **Scoring.** Bands were set with first-draft data known and are not re-tuned here. Kill bands compress all suites to 1–2. The readability score is one author's judgement. Ecosystem and FHIR scores are desk scores from 2026-11-07.

### 4. Recommendation

**Use pytest + httpx as the single tool for new API-level and access-policy tests.**

- It was the shortest suite with its helpers counted. Its 5×4 matrix is a plain-text table.
- An agent wrote 11 of 13 cases correctly on the first run. Both failures were wrong guesses about Aidbox.
- `expect_allow` and `expect_deny` put the decision, the crash check and the status behind one line. Its failure output named the policy by id in 4 of 5 diagnosis trials.
- It is the same language as aidbox-python-sdk apps, though this bake-off used raw httpx and did not exercise the SDK client. These numbers give no reason to adopt the spec's example split of "Hurl for policies + pytest for SDK flows" for new work.

**Keep the existing production suite running, and don't migrate it on this evidence.** Migrating it was not measured here. Hurl had the fastest runs and the simplest case files, and it killed the most mutants. Its weaknesses here are the status-only matrix and failure output that rarely names a policy. Decision assertions should address the second one, since the one Hurl trial that named a policy did so through a failing decision assertion.

**Build into the pytest setup before relying on it:** persist the transaction stamp so a killed run can be rolled back, which Tavern showed works on the same engine. Parallel runs would need the run opened outside xdist workers.

**What would change this recommendation.**

- **To Playwright:** the team is TypeScript-first, or fixtures and crash safety matter more than expressiveness. Equal weights or a Fixtures weight of 25 already put it first. Repeat authoring runs that close the AP or authorability gap would too.
- **To keeping Hurl for access policies:** a costed migration showing the move is not worth it, or a team that values no-helper test files above the matrix and diagnostics gaps. This is a cost argument the scores don't capture.
- **To Karate:** nothing tested here. It needs its authoring cost to fall and is third throughout, or tied second with Authorability removed.
- **Against pytest:** a repeat of the authoring run (N = 1) with results well below 11 of 13, or the user's readability review moving pytest down and Playwright up by a combined 2.5 steps.
- **At larger scale:** a real measurement at the existing production suite's size, if runner overhead turns out to dominate there. See the runtime limit below.

### 6. Limits

**Kill rate.**

- The 12–14 of 15 differences come from which rows each agent happened to write (mutants 07, 08, 09), not from framework capability. No suite killed 07, which is a spec gap: no case requires a request with an Encounter id under another type.
- Only 1 of 15 kills is decision-only (mutant 10). But ticket 04 built and verified the mutants by their probes flipping a verdict, so the set under-represents decision-only bugs. Don't read this as "status codes are enough". The diagnostic value of decision assertions is a separate matter: it is what named the policy in the time-to-diagnose trials.
- Every authoring run was told to read `sut/mutants/README.md`, which lists each mutant and its probe. Absolute kill rates are therefore optimistic.
- Karate: ticket 06's sanity sweep reported 13/15 untuned, and ticket 08 measured 12/15 (09 also survives). Case 14's flake may explain the earlier number, but that is unconfirmed. This report uses 12/15.

**Karate parallel runs.** Case 14 flakes under 4 threads because other features create `Bakeoff` Patients that its search can see. That is a data collision in this suite, not a defect in Karate. Karate's parallel warm runs failed 3 of 10 times. hyperfine kept no output for those runs, so the collision is unconfirmed as the cause.

**Authorability.** There was one authoring run per framework (N = 1), so a small part of any gap may be chance.

- Tavern is scored 0/13, noted as 9/13 after one shared fix.
- Python and TypeScript familiarity likely favours pytest and Playwright.
- pytest's run saw the truncated start (about 100 characters each) of the then-existing findings rows.
- Extra reads and probes differed per suite, from the ticket comments:

| Suite | Read beyond the listed files, or probed |
|---|---|
| Hurl | Reuses `sut/fixtures/run.sh` for setup. The ticket records no other reads or probes. |
| Karate | `sut/fixtures/fixtures.json` and `run.sh`. One live request to learn the debug shape. The SDC policy's debug trace during the case 9 fix. |
| pytest | `fixtures.json`, `run.sh`, `compose.yaml`, `smoke.sh`. Curl probes of the debug dump before the examples. |
| Playwright | `fixtures.json`, `run.sh`, `sut/mutants/revert.sh`. Hand probes of the debug dump and of a `$populate` body that case 3 relies on. |
| Tavern | `fixtures.json`, `run.sh`, `compose.yaml`, Tavern's installed source. About 9 curl requests in one probe run. |

**Runtime.** The suites span about 2.5–8.5 s for 15 cases on one four-core machine. That supports an ordering at this size and shows startup is small (floors of 0.23–1.10 s). It does not predict the existing production suite: Hurl ran about 80 requests here against far more there, no runtime for that suite is on record, and per-request overhead was not isolated. The small parallel gains (5–24%) suggest fixed setup and teardown dominate at this size, so parallelism could matter more at larger scale, but that is an inference. Tavern took 8.5 s for 93 tests against pytest's 3.05 s for 65, which hints at per-test cost, but the suites differ in what they do.

**Time-to-diagnose.** Grades are the author's and await the user's spot-check. 23 of 25 trials ran. Karate's and Playwright's results exclude mutant 09, the hardest of the five, because they never detected it. The agents were one model reading logs, not engineers.

**Hurl.** It runs 8.1.0 here and the existing production suite runs 8.0.1. Its case 8 asserts status only.

**Selection.** Tavern and Playwright joined by user decision, beyond the one extra slot of the within-10% rule. Desk scores and these scores use different bases, so they are not comparable.

**Scoring.** The bands were chosen with the raw data already known, and readability is one author's judgement. Ecosystem and FHIR scores are desk scores from 2026-11-07.
