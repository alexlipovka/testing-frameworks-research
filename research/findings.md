# Findings surfaced by each suite

Nuances about the SUT, the spec, or Aidbox that a framework's suite surfaced while being written. Each suite adds its own; the final revision pass (after ticket 09) feeds them back into every suite and the spec.

| # | Surfaced by | Kind | Finding | Follow-up |
|---|---|---|---|---|
| - | pytest | Aidbox | `__debug=policy` always answers 200 with the dump, even for writes and for denied requests, so the decision has to come from `policies[].eval-result`. A SQL policy that denies shows `eval-result: false` or `null` (null when the query returns no row), so "deny" means no policy is `true`, not "some policy is `false`". | Suites that look for `eval-result == false` miss the null denies; check every suite's helper. |
| - | pytest | Aidbox | An AccessPolicy with `link: [{reference: "User/<id>"}]` never applies to that user's password-grant session: debug shows `reason: "no links"`. Scoping by `roleName` with a run-unique Role works. | Check whether 2608 expects a different link form for Users, or whether User links only match other auth flows. |
| - | pytest | Aidbox | A SQL policy that throws (`SELECT 1/0 = 1`) appears in the debug dump as `error: "ERROR: division by zero"` with `eval-result: null`. The real request gets a plain 403 that looks exactly like a deny, so only the debug dump tells them apart. | Case 3 in every suite should assert on `policies[].error`, not just on status. |
| - | pytest | Aidbox | In a transaction-response, `entry[].response.location` is an absolute URL with host and `_history` (`http://host/fhir/Observation/<id>/_history/<v>`), not a relative `Observation/<id>`. | none |
| - | pytest | Spec gap | Case 3 needs a policy that throws, and the baseline has none. The pytest suite adds a run-scoped Role and throwing policy mid-run, which the teardown deletes. That bends "never change policies during a run", which is about the baseline, but it isn't written down. | Say in policies/README whether a run-scoped extra policy is allowed, so all suites do case 3 the same way. |
| - | pytest | Spec gap | Case 15 ("two consecutive runs green") belongs to the runner, not to any single test. The pytest suite does both: `RUNS=2 ./run.sh`, plus an in-run test that stamps, writes, rolls back and checks the write is gone. That nested rollback is only safe while tests run sequentially. | Define case 15 the same way for every suite before comparing LOC. |
| - | pytest | Framework | A session-scoped fixture under pytest-xdist runs once per worker, so N workers would open N runs at once and break "one run at a time per stack" (each teardown deletes the others' rows). | For the parallel benchmark, open the run outside pytest (or in the xdist controller) and pass run_id, tx_id and tokens to the workers. |
| - | pytest | Framework | httpx `json=` always sets `application/json`, so JSON Patch and merge-patch need `content=json.dumps(...)` with an explicit Content-Type. Otherwise Aidbox would see a plain JSON body. | none |
